# REVIEW_PROCESS – UniCloud, Екип 2

Задача в борда: #66.

`main` е защитен: всеки PR се слива само след поне едно одобрение. За да не чакат PR-ите, всеки член на екипа има **отговорен рецензент** – човек от друга роля, който отговаря прегледът да бъде направен навреме.

**Всеки може да рецензира всеки.** Отговорният рецензент не е единственият – той е този, който **гарантира**, че прегледът е направен.

Всеки е отговорен рецензент на **точно един** човек, за да е равно натоварването.

## Правила

1. **Създаване на PR** – посочи отговорния си рецензент още при създаването:
   ```bash
   gh pr create --fill --reviewer <отговорен рецензент>
   ```
   Пример за Златин: `gh pr create --fill --reviewer danielgeorgiev10`
2. **Срок** – отговорният рецензент прави прегледа **до 24 часа**. Ако не може (болен, зает), казва в чата и авторът добавя резервния:
   ```bash
   gh pr edit <номер> --add-reviewer <резервен рецензент>
   ```
3. **Код от чужда област** – ако PR променя код, който е на друга роля (напр. Security променя backend), добави и собственика на кода като рецензент.
4. **Резултат от прегледа** – *Approve* (одобрявам), *Request changes* (поправи и ще погледна пак) или коментар с въпрос. След поправки рецензентът преглежда отново до 24 часа.
5. **Сливане** – само авторът слива, и то след одобрение. Никакво `--admin` и никакво заобикаляне на защитата.
6. **Standup** – всеки отговорен рецензент казва дали има чакащи PR-и към него. Чакащите PR-и на всички се виждат с:
   ```bash
   gh pr list --search "review:required"
   ```

## Какво проверява рецензентът

- [ ] PR-ът е свързан със задача (`closes #N` в описанието или commit-а).
- [ ] Критерият за приемане на задачата е изпълнен.
- [ ] CI минава (build, тестове, проверки за сигурност).
- [ ] Няма пароли, токени и тайни в кода.
- [ ] Спазени са `API_CONTRACTS.md` и правата по роли.
- [ ] Кодът е разбираем; ако не е – въпрос в коментар, не директна поправка от рецензента.
- [ ] PR-ът е малък – една задача, един PR.
