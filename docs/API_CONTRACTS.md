# API_CONTRACTS – UniCloud, Екип 2

**Статус:** Седмица 1 – Екип 1 отговори (2026-11-15), чакаме потвърждение по останалите точки и от Екипи 3 и 4.
**Отговорници:** Радостин Павлов (PM), Златин Златинов (SE 1 – API), Стилиян Тодоричков (SE 3 – интеграции).
**Пълна спецификация:** OpenAPI (Swagger UI) на `/swagger-ui.html` – поддържа се от SE 1. Този документ описва договореностите; при разлика важи OpenAPI спецификацията, а този документ се обновява.

## 1. Общи правила

| Правило | Договорка |
| --- | --- |
| Адрес | `https://<домейн>/api/v1/...` |
| Версия | в пътя (`/v1`); несъвместима промяна → `/v2`, старата версия работи още поне 2 седмици |
| Формат | JSON, UTF-8; имената на полетата в camelCase |
| Дати и часове | ISO 8601 в UTC, напр. `2026-11-16T06:15:00Z` |
| Идентификатори | UUID като текст |
| Идентификатор на курс | общ за всички екипи: `courseOfferingId` – числовият ID на предлагането на дисциплината за семестъра от портала на Екип 1, напр. `101`. Екип 1 е източникът на тези ID. Текстов код (`courseCode`, напр. `OIT-2026W`) се ползва само за показване, не за обмен |
| Вход | `Authorization: Bearer <JWT>` (вж. раздел 3) |
| Страници | `?page=0&size=20` (най-много 100); отговорът съдържа `content`, `page`, `size`, `totalElements` |
| Кеш | публичните отговори имат `Cache-Control: public, max-age=60`; личните – `private, no-store` |
| Ограничение на заявките | при надвишаване – `429 Too Many Requests` с `Retry-After` |

### Формат на грешките

```json
{
  "status": 403,
  "error": "FORBIDDEN",
  "message": "Нямате права за тази операция.",
  "path": "/api/v1/courses/7f1c.../modules",
  "timestamp": "2026-11-16T06:15:02Z"
}
```

| Код | Кога |
| --- | --- |
| 400 | невалидни данни (с поле `fields` – списък с грешките по полета) |
| 401 | липсва или е невалиден токен |
| 403 | токенът е валиден, но ролята няма право |
| 404 | ресурсът не съществува **или** потребителят няма право да знае, че съществува |
| 409 | конфликт (напр. дублиран код на курс) |
| 413 | прекалено голям файл |
| 415 | непозволен тип файл |
| 429 | твърде много заявки |
| 5xx | грешка при нас – брои се срещу error budget |

## 2. Вътрешно API (за SE 2 – Frontend)

| Метод и път | Кой | Описание |

| `PUT /courses/{courseId}` · `DELETE /courses/{courseId}` | собственик, админ | промяна / изтриване |

| `POST /modules/{moduleId}/lessons` | собственик | ново занятие |
| `GET /lessons/{lessonId}/materials` | всички | материалите към занятие |
| `POST /lessons/{lessonId}/materials` | собственик | нов материал (`multipart/form-data` за файл или JSON за препратка) |
| `GET /materials/{materialId}` | всички | материал с текущата версия |
| `PATCH /materials/{materialId}` | собственик | описание, тагове, скриване |

| `GET /materials/{materialId}/file?version=N` | всички; служебният токен на Екип 3 – само за `ASSIGNMENT` | файлът (пренасочване към кеширан адрес) |
| `GET /search?q=&discipline=&teacher=&topic=&page=&size=` | всички | търсене (SE 1) |
| `PUT /materials/{materialId}/read` · `DELETE /materials/{materialId}/read` | студент | отметка „прочетено“ / премахване (SE 3) |
| `GET /courses/{courseId}/progress` | студент | собствените отметки за курса (SE 3) |
| `POST /auth/login` | всички | временен вход с демо акаунти (Седмица 1) |
| `GET /actuator/health` | Nginx, мониторинг | liveness / readiness (без `/api/v1`) |

### Материал (пример)

```json
{
  "id": "3b2e8c1a-...",
  "lessonId": "91d0...",
  "courseOfferingId": 101,
  "courseCode": "OIT-2026W",
  "type": "PRESENTATION",
  "title": "Лекция 1 – Въведение в облачните изчисления",
  "description": "Слайдове от първата лекция",
  "tags": ["облак", "въведение"],
  "currentVersion": 2,
  "fileUrl": "https://<домейн>/files/3b2e.../v2/lecture1.pdf",
  "videoUrl": null,
  "hidden": false,

```

Типове материали: `NOTES` (конспект), `PRESENTATION`, `VIDEO_LINK`, `ASSIGNMENT` (условие на задача), `LITERATURE`.
Позволени файлове: PDF, PPTX, DOCX, PNG, JPG; до 50 MB (решение на Security – UC-13).

## 3. Екип 1 – Портал и идентичност (Екип 1 → Екип 2)

**Какво:** кой е потребителят, ролята му и в кои курсове е записан.
**Как:** JWT токен, издаден от портала на Екип 1. Екип 1 няма възражение срещу подпис с публичен ключ; алгоритъмът (предлагаме RS256) и JWKS адресът предстои да се потвърдят.

Токен по примера на Екип 1 (2026-11-15), с промените, които предлагаме:

```json
{
  "iss": "unicloud-portal",
  "aud": "unicloud-api",
  "sub": "9",
  "role": "STUDENT",
  "permissions": ["STUDENT_PROFILE_READ_OWN", "COURSE_OFFERING_READ", "ENROLLMENT_REQUEST_CREATE"],
  "courses": [101, 205],
  "iat": 1794654504,
  "exp": 1794656304
}
```

| Поле | Договорка | Статус |
| --- | --- | --- |
| `iss` | `unicloud-portal` | по примера на Екип 1 |
| `aud` | `unicloud-api` | по примера на Екип 1 |
| `sub` | постоянният ID на акаунта в портала (текст, напр. `"9"`); без имейл и ЕГН; не се преизползва за друг човек | Екип 1 потвърждава дали ще е точно този ID |
| `role` | **една** текстова стойност: `STUDENT`, `TEACHER`, `ADMIN` или `INSPECTOR` (Екип 1 сменя масива `roles` с едно поле `role`) | прието |
| `permissions` | списък с правата в портала; UniCloud ги чете, но в Седмица 1 решава достъпа по `role` (вж. таблицата долу) | прието |
| `courses` | числовите `courseOfferingId` на курсовете, в които потребителят е записан | **предложение** – в токена на Екип 1 още липсва |
| `exp` | 30 минути (сегашният срок на Екип 1); приемаме всичко до 1 час | прието |

**Защо до 1 час:** токенът стои в браузъра; ако изтече, вреда може да се нанесе само докато е валиден. Кратък срок ограничава риска, а лекцията е 45–90 минути, така че студентът ще получи нов токен от портала най-много веднъж-дваж. При изтекъл токен UniCloud връща `401` и интерфейсът пренасочва към портала.

**Роли в UniCloud:**

| Роля | Какво може в UniCloud |
| --- | --- |
| `STUDENT` | чете материали, търси, отбелязва „прочетено“ (само своите отметки) |
| `TEACHER` | като студент + създава и променя своите курсове и материали |
| `ADMIN` | всичко |
| `INSPECTOR` | **предложение:** само преглед на всички курсове и материали, без отметки и без промени – чака потвърждение какво прави тази роля в портала |

Непозната роля → достъп само за четене на публичния каталог.

**Седмица 1:** UniCloud издава временни токени със същите полета (демо акаунти), за да не се преправя кодът при свързването с Екип 1. Ограничаването по `courses` е за следваща седмица.

## 4. Екип 3 – Автоматично оценяване (Екип 2 → Екип 3)

**Какво:** условията на курсовите задачи (материали от тип `ASSIGNMENT`).
**Как:** REST, само четене; Екип 3 се идентифицира със собствен токен за услуга (`role: SERVICE`).
**Документация на Екип 3:** https://github.com/AutoJudgeLab/UniCloudAutoJudge/tree/main/docs

### 4.1 Кой какво притежава

| Данни | Собственик | Бележка |
| --- | --- | --- |
| Курсът и записаните студенти | Екип 1 | `courseOfferingId` |
| Файлът с условието и неговите версии | **Екип 2** | материал от тип `ASSIGNMENT` |
| Заданието за оценяване: заглавие, максимални точки, **краен срок**, ревизии | **Екип 3** | вече реализирано при тях (`POST /api/assignments`, `deadline`, ревизии) |
| Тестови случаи, предавания, изпълнение, оценки | **Екип 3** | |

**Краен срок:** управлява се **само от Екип 3**. Тяхната система вече проверява срока при всяко предаване, затова един източник на истина избягва разминаване. UniCloud не пази срок; ако се показва на студентите, се чете от API-то на Екип 3.

**Връзка между двете системи:** заданието при Екип 3 пази `courseOfferingId`, `statementMaterialId` (ID на материала в UniCloud) и `statementVersion` (версията на условието, по която е ревизията).

**Какво UniCloud НЕ прави** (за да няма дублиране): не създава и не управлява задания за оценяване, не пази крайни срокове, тестове, предавания и оценки. Всичко това е при Екип 3. Преподавателят създава заданието в системата на Екип 3, а файла с условието качва в UniCloud.

### Идентификатори

| Идентификатор | Чий е | Тип | Пример |
| --- | --- | --- | --- |
| `courseOfferingId` | Екип 1 | число | `101` – същото, което Екип 1 и Екип 3 обсъждат като `courseId`; името ще съвпадне с това на Екип 1 |
| `materialId` | Екип 2 | UUID | условието на задачата в UniCloud |
| `version` | Екип 2 | число | версия на файла с условието (1, 2, …) |
| `assignmentId` | Екип 3 | UUID | заданието за оценяване |
| `assignmentRevisionId` | Екип 3 | – | ревизията на заданието |

По желание (P2) UniCloud може да пази и `assignmentId` на Екип 3 към материала, за да показва линк „Предай решение“ от страницата на условието.

### 4.2 Списък със задачите по курс

`GET /api/v1/integrations/assignments?courseOfferingId=101&page=0&size=50`

С пагинация, както всички списъци при нас (раздел 1), най-много 100 на страница:

```json
{
  "content": [
    {
      "materialId": "c41f...",
      "courseOfferingId": 101,
      "title": "Курсова задача 1 – Docker",
      "version": 2,
      "fileUrl": "https://<домейн>/api/v1/materials/c41f.../file?version=2",
      "sha256": "9f2c...",
      "updatedAt": "2026-11-15T10:00:00Z"
    }
  ],
  "page": 0,
  "size": 50,
  "totalElements": 1
}
```

Връщат се само видимите (нескрити) условия. `sha256` позволява на Екип 3 да провери, че е изтеглил точно този файл.

### 4.3 Изтегляне на файла

`GET /api/v1/materials/{materialId}/file?version=N` с `Authorization: Bearer <служебен токен>` – **да**, служебният токен на Екип 3 може да изтегля файловете на материали от тип `ASSIGNMENT` (само тях). Без `version` се връща текущата версия.

### 4.4 Версии на условието

- Вече предадените решения и оценките им остават към версията, по която са предадени; **без автоматично преоценяване** (предложение на Екип 3 – прието).
- При нова версия на файла `version` се увеличава. Екип 3 разбира за нея от списъка в 4.2 и решава дали да създаде нова ревизия на заданието.
- По-късно (P2): събитие `material.uploaded` към Екип 3, за да не се налага да проверяват периодично.

### 4.5 Тестове

Тестовите случаи, включително кои са публични и кои скрити, се създават, съхраняват и показват **само в системата на Екип 3**. UniCloud не съхранява тестове. Ако преподавателят иска примерни входни и изходни данни в условието, ги пише в самия файл с условието; те не се ползват за оценяване.

## 5. Екип 4 – Анализи и AI Ментор (Екип 2 → Екип 4)

### 5.1 Събития за прочетеното

**Как:** UniCloud изпраща `POST` към адрес на Екип 4 (webhook) при всяко събитие (потвърдено от Екип 4 на 2026-11-19). Адресът на приемника – Екип 4 ще го изпрати след deploy.

```json
{
  "eventId": "e7a1...",
  "type": "material.read",
  "occurredAt": "2026-11-16T06:17:43Z",
  "userId": "p-5d9e1b",
  "courseOfferingId": 101,
  "materialId": "3b2e8c1a-...",
  "version": 2
}
```

| Поле | Договорка | Статус |
| --- | --- | --- |
| `type` | `material.viewed` (студентът е отворил материала), `material.read` (изрично отбелязан като прочетен), `material.unread` (отметката е премахната), `material.uploaded` (нов материал или версия) | `viewed` и `read` – **потвърдени** от Екип 4 |
| `userId` | **псевдоним** (HMAC-SHA256 от `sub` с тайна, която е само при UniCloud), напр. `p-5d9e1b`. Един и същ студент има винаги един и същ псевдоним. Не се изпращат имена, имейли, `sub` или друга лична информация (вж. `GDPR_DATA_PROTECTION.md`) | **потвърдено** |
| `eventId` | уникален UUID; Екип 4 игнорира повторно получени събития | **потвърдено** |
| останалите полета | `occurredAt`, `courseOfferingId`, `materialId`, `version` | **потвърдени** като достатъчни |

**`material.viewed` – колко често:** най-много едно събитие на студент и материал за 30 минути, за да не се изпраща събитие при всяко презареждане на страницата (предложение).

Псевдонимът остава личен данен по GDPR (псевдонимизирани данни), затова Екип 4 не трябва да се опитва да свърже `userId` с конкретен човек.

### 5.2 Подпис на заявките

| Заглавка | Съдържание |
| --- | --- |
| `Content-Type` | `application/json` |
| `X-UniCloud-Event-Id` | същото като `eventId` в тялото |
| `X-UniCloud-Timestamp` | времето на изпращане, Unix секунди, напр. `1795330663` |
| `X-UniCloud-Signature` | `sha256=` + HMAC-SHA256 в hex на низа `<X-UniCloud-Timestamp>.<тялото на заявката точно както е изпратено>` със споделената тайна |

**Проверка при Екип 4:**
1. Изчислява HMAC-SHA256 на `<timestamp>.<сурово тяло>` с тайната и го сравнява с подписа чрез сравнение с постоянно време (constant-time).
2. Отказва заявки, по-стари от 5 минути (защита от повторно изпращане на чужда заявка).
3. Отговаря с `2xx` до 5 секунди; при `5xx` или изтекло време UniCloud опитва отново до 3 пъти (след 10 s, 1 min, 5 min).

Пример за низа, който се подписва: `1795330663.{"eventId":"e7a1...","type":"material.read",...}`

**Тайната:**
- поне 32 случайни байта (напр. `openssl rand -hex 32`);
- генерира се от Екип 2 и се предава **по защитен канал**: лично или с еднократна връзка, която изтича след прочитане. Никога в Git, в issue или в общ чат;
- при нас се пази като secret в средата (GitHub Actions secret / променлива на средата), при тях – по същия начин;
- при смяна на тайната за кратко се приемат и двете (старата и новата).

Отговорници: Стилиян Тодоричков (SE 3, изпращането) и Хадел Мислими (Security, тайната).

**Седмица 1:** събитията се записват при нас в този формат; показва се поне едно примерно изпращане (реално или към фалшив адрес), докато Екип 4 изпрати адреса.

### 5.3 Текст на материалите за AI Ментор

`GET /api/v1/integrations/materials/{materialId}/text` → извлеченият текст от PDF / PPTX. Нужен е на Екип 4 само за AI Ментора, не за аналитиката. **Реализация – следващата седмица** (потвърдено от Екип 4).
